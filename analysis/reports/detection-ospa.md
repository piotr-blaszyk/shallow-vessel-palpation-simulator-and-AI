# Vessel localisation scored as a detection problem: counts, matching and OSPA

*2026-09-04. Companion to `reports/ours-same-metric-derivations.md` and
`reports/vessel-centreline-derivations.md`. Generated by `scripts/detection_ospa_report.py`
from `results/detection_ospa.json`; the numbers are never retyped.*

---

## Why

Every distance on the poster is a mean over things that were assumed to correspond: pixel to
nearest pixel, centroid to centroid. None of them says how many vessels the model found, and a
mean over matched objects quietly rewards a model that predicts the one easy vessel and skips
the hard ones. A frame or a map here holds **0, 1, 2 or 3** vessels, so the task is a detection
problem, and it is scored the way object detection and multi-target tracking are scored:
extract objects, match them, then report **counts**, **detection rates** and **localisation
error** separately, plus one penalised scalar for model selection.

## The metric

Objects are matched with the Hungarian algorithm and scored with **OSPA** (Schuhmacher, Vo &
Vo, 2008), the standard distance between two sets of different cardinality, with an asymmetric
cardinality penalty:

```
d = [ SUM_matched min(d_i, c)  +  c * (a_FP * FP + a_FN * FN) ] / max(m, n)
```

| parameter | value | where it comes from |
|---|---|---|
| `c` = `tau` | **5 mm** | the clinical usefulness threshold: the distance beyond which a localisation is useless here. Set by judgement, not tuned on the data. |
| `a_FP` | **2** | a false vessel costs twice a missed one: it sends a needle into tissue, whereas a miss only forfeits the assist. |
| `a_FN` | **1** | reference weight. |
| `p` | **1** | so OSPA is an average in millimetres. |

`m` = predicted objects, `n` = true objects. Because both weights are >= 1, pairing is never
dearer than leaving a pair unmatched, so the optimal assignment matches `min(m, n)` objects and
the cardinality error is `|m - n|`. Two empty sets score 0; the metric is bounded above by
`max(a_FP, a_FN) * c` = **10 mm**, the score of a data point that is all false alarms.

The cutoff was **1 mm** when this was first written (the error margin for IV needle access)
and was raised to **5 mm** by the user on 2026-09-04. Both are reported below rather than
only the current one, because the choice of `c` is a judgement and it moves every number.

Reported **beside** OSPA, never instead of it, because OSPA alone cannot separate a
localisation error from a detection error: the count confusion matrix, precision / recall / F1
at `tau`, and the mean distance over matched pairs.

## Extraction

Two object types, because "where is the vessel" has two natural answers:

* **centreline** --- one straight segment per vessel, total-least-squares fit. Distance between
  two centrelines is the symmetric mean point-to-segment distance (25 samples per segment).
* **centroid** --- one point per vessel. Distance is plain Euclidean, in mm.

...and two spaces, which differ in what is on disk:

* **Video-frame space** carries the model's **per-marker probabilities** (`probs` in the saved
  npz, 0.10--0.999), so the prediction side uses a **heatmap head**: non-maximum suppression over
  the score field picks peaks, every above-threshold marker joins its nearest peak, and each
  object's centroid and axis are **score-weighted**, which localises below the ~2 mm marker
  pitch. Plain radial NMS would shred an elongated vessel into one object per bump, so a peak is
  only allowed to split a connected component when the peaks are more than `R_SPLIT` = 3.0 mm
  apart **and** the score dips below 0.80 x the weaker peak between them --- a watershed in spirit.
  `R_SPLIT` sits below the smallest true vessel separation in the data (3.5 mm) and above the
  marker pitch (1.8--2.0 mm).
* **Top-view map space** has only the thresholded masks on disk --- no probability map is saved by
  the map builder --- so extraction there is plain connected components with an unweighted
  centroid and axis, and **no heatmap head is used**.

Near-duplicates are merged in both spaces so a fragmented mask cannot over-count: centroids
closer than 2 mm, or centrelines within 12 deg of each other, offset by less than 2 mm
**and overlapping along their shared axis**. That last clause matters: without it the silicone
phantom's left- and right-hand sweeps of the same row, which are collinear but disjoint, were
fused into one object and the ground-truth count came out as 8 instead of 10.

## Pictures of the final matched state

`scripts/detection_overlays.py` draws one image per data point showing **exactly the objects
scored above**, after filtering and after matching --- no candidate peaks, no pre-merge
fragments. Current run: **`analysis/overlays/detections/<stamp>`**
(3465 images, 179 MB, `tau` = 5 mm).

| style | meaning |
|---|---|
| magenta / orange | ground truth / prediction |
| solid, label `k` | matched pair, within the tolerance |
| solid thin, label `k*` | matched pair, but farther apart than the tolerance |
| dashed line, hollow dot, label `(k)` | **unmatched** object |

A magenta `k` and an orange `k` are the same pair; an index that appears in only one colour is
unmatched. Markers and pixels keep the confusion colours (TP green, FN red, FP blue, TN grey),
and every title lists the pair distances and that data point's OSPA. Three variants per data
point: `centreline/`, `centroid/`, and `both/` (the centreline objects with their segment and
their centroid drawn together, matched as centrelines). The bulk frame-space images and the
contact sheets are git-ignored; the top-view images and the manifests are tracked.

## What the numbers say

**OSPA orders the four transfers, and it is the first single number on this project that
does.** Video-frame space, centrelines: Sim->Sim **0.91**, Sim->Silicone **3.20**, Sim->Meat **5.07**, Meat->Silicone **5.97** mm; F1 at the same
tolerance runs 0.85 / 0.77 / 0.42 / 0.37 in the same order. The
poster's distance columns do not order them this way, because they never charge for a vessel
that was invented or missed.

**Sim->Sim is the one configuration that works.** Its top-view map finds exactly one vessel where
there is exactly one, at 0.36 mm, with precision, recall and F1 all 1.00. Per frame it holds
up too: 290 true detections against 70 false alarms and 32 misses (P 0.81, R 0.90), and
the pairs it does make sit 1.35 mm apart on average.

**Detection degrades faster than localisation.** On Sim->Silicone the model still finds most vessels
(F1 0.77 per frame) but its OSPA is 3.20 mm; by Meat->Silicone F1 is 0.37 and OSPA 5.97 mm.
Count accuracy tells the same story: 0.90 -> 0.63 -> 0.36 -> 0.24. The confusion matrices show where it goes ---
Sim->Meat and Meat->Silicone over-predict, splitting one vessel into two or three, or inventing them where the
ground truth is empty.

**The matched-only distance is not a metric on its own, and the silicone map proves it.** There
the mean over all matched pairs is **13.87 mm**: with 10 true sweeps and 13 predicted objects,
the Hungarian assignment pairs a sweep at one end of the phantom with one at the other. Restrict
to pairs inside the tolerance and it falls to 1.38 mm over 5 pairs --- a different quantity
entirely. Both are in the tables above so the gap is visible.

**The asymmetric penalty does the work it was asked to do.** Meat->Silicone's 26 vessel-free frames score
OSPA **10.00 mm** --- the maximum the metric can take, `max(a_FP, a_FN) * c` = 10 mm --- because
every one of them contains a false alarm and a false alarm is charged twice a miss. That is the
100 % false-alarm rate, which the poster keeps as spoken material, produced by the metric itself.

**Raising the cutoff from 1 mm to 5 mm changes the verdict from "nothing works" to "one
thing works and the rest are noisy".** At 1 mm almost no pair survived the gate, so every
detection rate was near zero and OSPA was dominated by the cardinality term; at 5 mm the
detection rates become informative and the localisation error starts to matter. Neither cutoff
is more correct --- 1 mm is the needle-access margin, 5 mm is nearer a vessel diameter --- which
is why both are in the table above.

## Caveats

* **This is a heatmap head bolted onto a segmentation head, not a trained one.** The saved
  per-marker probabilities are used as the score field, which is the right thing to do with what
  is on disk, but a model trained to regress a Gaussian at each vessel would give points directly
  instead of inheriting segmentation errors non-linearly. Changing that is a model-design change
  and a retraining job, not a metric recomputation.
* **Top-view space gets no heatmap head at all**, because the map builder saves only thresholded
  masks. It holds a float `maxprob` map in memory (`vessel_map.py::MapData.maxprob`) and discards
  it. Saving it would let the same extraction run there, and would very likely improve the
  top-view counts, where the silicone map over-counts 10 true sweeps as 13.
* **OSPA scales with `c`.** An absolute value is not "the system is 5 mm accurate"; it is a
  blend of localisation error and cardinality error on a scale set by the cutoff. Read the
  ordering and the F1 column, not the millimetres alone.
* **The `R_SPLIT` = 3.0 mm splitting rule is data-dependent.** It works because the smallest true
  vessel separation in these datasets is 3.5 mm. A dataset with vessels closer than that would
  need the rule re-derived, or a proper watershed on a distance transform.

## Reproduction

```bash
python analysis/scripts/detection_ospa.py         # analysis/results/detection_ospa.json  (~4 min)
python analysis/scripts/detection_ospa_report.py  # this file
python analysis/scripts/detection_overlays.py     # the overlays  (~7 min, 3465 images)
```

`detection_ospa.py --cutoffs 5 1` sets the cutoffs; `detection_overlays.py
--tau 5` sets the one the pictures are drawn at. All parameters are recorded in the JSON's
`params` block and in each overlay run's `params.json`.
